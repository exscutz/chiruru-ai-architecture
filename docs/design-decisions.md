Six decisions that shape Chiruru's architecture. Each one is implemented in the current production system (November 2026). They are written up from the project's internal decision records and the code.

## 1. Local LLM generates live speech, cloud LLM only supports it

**Problem.**

- **What the live show needs.** Continuous speech for hours, a stable persona, and no dependence on an external service being reachable.
- **What the cloud offers.** Frontier models are much stronger at planning and judging, such as deciding which stories form a coherent show.

**Alternatives considered.**

- **A. Cloud LLM for everything.** This gives the best quality per call. The costs are network latency inside the speech loop, rate limits and outages during the broadcast, and a persona voice tied to a vendor model.
- **B. Local for everything.** This is fully self-contained, but planning and evaluation quality is limited to what a workstation-class local model can do.
- **C. Split by role.** The local model generates all live speech. The cloud model handles planning and analysis, and may add optional context, but never generates speech.

**Decision.** C.

- **During the stream.** All live speech, news scoring, and memory work runs on a locally hosted model.
- **Optional context during the stream.** A background step can gather external reaction context for the current topic. The show does not wait for it. If the context is not ready in time, the optional segment is skipped. When it is used, it is input material for the local model.
- **Before the stream.** A cloud editorial step runs only in the preparation phase. The editorial step itself is never called during the stream. Its output is a topic-order cursor plus short labels. These reach the prompt only through a fixed template.
- **After the stream.** Cloud models score and analyse what was already broadcast.
- **What the cloud never writes.** Lines spoken in the live stream, and the characters' opinions, inner voice, and self-interpretation, are never generated by the cloud model.

**Trade-offs.**

- ➕ The broadcast survives cloud outages. If the editorial step fails, the show falls back to local topic selection.
- ➕ The persona voice comes from one model under the operator's control.
- ➖ Live speech quality is capped by the local model.
- ➖ The optional in-broadcast context adds a background cloud dependency. Its failures do not stop the show, but they need to be monitored.
- ➖ Cloud usage is spread across offline modules rather than sitting behind one routing layer, so the boundary is enforced by design rules and review, not by the type system.

## 2. One serialized queue for live speech, with self-healing

**Problem.**

- **Shared server.** Many components need the same local LLM server: speech, chat replies, scoring, summarisation, and digests.
- **Contention.** If they call it concurrently, the server slows down for everyone.
- **Stalls.** The server occasionally stalls, and a stalled model means silence on air.

**Alternatives considered.**

- **A. Each caller calls the server directly, with its own timeouts.** This is simple, but there is no prioritisation, and a burst of background work can starve live speech.
- **B. Run several model instances.** This is limited by GPU memory on a single workstation.
- **C. One queue in the bot, plus an external watchdog.**

**Decision.** C, with the watchdog inside the bot.

- **The queue.** Live speech generation goes through one execution queue: a single worker, a priority queue, a timeout per job, and a tag recording which component submitted each job. Some background and supporting operations, such as scoring and memory work, still use separate inference paths.
- **Timeouts.** Each call's timeout is kept below the queue's outer limit, so timeouts nest predictably.
- **The recovery service.** It watches runtime signals, confirms a stall before acting, and then reloads the model through the inference server's management interface.
- **Recovery limits.** It acts only on confirmed state, never on a guess, and its reloads are rate-limited.

**Trade-offs.**

- ➕ Predictable latency for high-priority work, and one place to observe LLM load.
- ➕ Stalls recover without the operator stepping in, and the limits stop the watchdog from causing a reload loop.
- ➖ Throughput is serialized by design.
- ➖ The queue does not give exclusive control of the inference server. Background paths outside it can still compete with live speech for the same server.

## 3. Post-stream automation: in-process trigger, out-of-process worker, receipts

**Problem.**

- **The work.** After every stream, a series of jobs must run unattended: description, thumbnail, Shorts, highlight video, analytics, and reports.
- **How they fail.** Each depends on a different external service or resource.
- **Past failures.** An earlier version lost a full night's output because the recording-completion signal could not be trusted.

**Alternatives considered.**

- **A. A fixed-time systemd timer.** This is decoupled from the bot, but it does not know when the recording actually finished.
- **B. Run the jobs inside the bot process.** This knows the right moment, but it mixes heavy batch work with the live process and its lifetime.
- **C. The bot arms a trigger, and a separate worker does the work.**

**Decision.** C.

- **The trigger.** When the stream ends and its recording record is saved, the live bot passes that record straight to an in-process **sweeper**. The sweeper uses it directly and does not query a shared database.
- **The retry schedule.** The sweeper starts the post-stream systemd oneshot without blocking: first after a delay, then periodically, for a bounded number of attempts.
- **The worker.** It runs under a lock and does not run when its preconditions cannot be confirmed.
- **Receipts.** Each action's receipt separates success, retryable failure, and terminal failure, within a bounded retry budget. Temporary resource contention does not consume the budget.
- **YouTube writes.** These are serialized.

**Trade-offs.**

- ➕ Re-running is always safe, and a partial failure resumes where it stopped.
- ➕ Heavy work never shares a process with the live show.
- ➖ More moving parts: a sweeper, a unit, receipts, and a lock.
- ➖ A failure of the trigger itself would leave work unstarted. A catch-up check at bot start and a manual recovery procedure cover that case.

## 4. Streamed speech with playback-anchored subtitles and fail-open playback

**Problem.**

- **Latency.** Waiting for a full LLM response and then synthesizing it adds seconds of dead air.
- **Audio device stalls.** Audio device calls can block in native code. On an asyncio event loop that freezes the whole show.
- **Subtitle timing.** Subtitles timed to text generation drift away from the audio.

**Alternatives considered.**

- **A. Whole-response synthesis.** This is simple but slow to start.
- **B. Stream tokens straight to TTS.** Prosody suffers when the text is split mid-phrase.
- **C. Stream at sentence and comma granularity.** Isolate device I/O, and tie subtitles to playback.

**Decision.** C.

- **Chunking.** Streamed LLM output is buffered and cut at sentence and comma boundaries.
- **Synthesis.** Each chunk is streamed through a self-hosted TTS server, reached through a pluggable backend interface.
  - A guard stops a chunk whose audio runs far longer than its text should.
  - If streaming fails *before* playback starts, the chunk can be synthesized as a whole file instead. Once playback has started, there is no fallback.
- **Device I/O.** Opening, starting, and closing the audio device run on a dedicated thread pool, with a time limit on close.
- **Subtitles.** A subtitle appears when its audio starts playing. Show and hide events are logged as the timing source of truth.
- **Failures.** If a single utterance fails, it is logged and skipped, and the queue keeps playing.

**Trade-offs.**

- ➕ Speech starts after the first sentence is ready, a stuck device call cannot freeze the event loop, and subtitles match the audio.
- ➖ An utterance can be cut short by a skipped chunk. This is accepted, because silence or a frozen show is worse.
- ➖ The chunking settings trade latency against prosody and need tuning per voice.

## 5. Prompt composition has one owner, and prompt changes are classified before rollout

**Problem.**

- **Duplicated blocks.** Over time, the chat-reply system prompt came to be assembled by several code paths. The same persona and platform blocks could appear up to five times.
- **Unclear evidence.** For any prompt change, it was unclear what evidence was needed before shipping it. Running everything through live A/B tests was slow, and much of it was unnecessary.

**Alternatives considered.**

- **A. Keep the many composers and deduplicate the text afterwards.** This is fragile, and the order of blocks stays implicit.
- **B. Require a live A/B test for every prompt change.** It is statistically clean, but too slow for fixing defects or making structural changes, and A/B tests can interfere with each other.
- **C. One composer per prompt, and a classification step for every change.**

**Decision.** C.

- **One composer.** A single compiler owns the chat-reply system prompt and emits each canonical block exactly once. If a required component is missing, it falls back to the previous composition.
- **Classification.** Before any prompt, persona, or prompt-builder change, it is classified as one of:
  - byte-identical;
  - structural;
  - persona projection;
  - new information supply;
  - quality comparison;
  - defect fix.
- **When A/B is used.** A live A/B test is required **only** when the change claims a quality difference. The other classes ship as direct edits. They still need an offline defect screen, the operator's approval, a rollback procedure, and monitoring after release.
- **Offline harnesses.** These must reproduce the production-rendered input before their results count, because a harness that is better supplied than production hides failures.

**Trade-offs.**

- ➕ Prompt structure is explicit, each prompt has one place to change, and the token cost is lower.
- ➕ Each change needs only the evidence that matches its risk.
- ➖ Classification needs judgment and discipline, and some of it is enforced by process rather than tooling.
- ➖ Prompt text files are cached in memory, so both rollout and rollback need a restart outside broadcast hours.

## 6. Two characters on one model: profiles on a shared pipeline

**Problem.**

- **What a second character needs.** Its own identity, voice, and memory on air.
- **The constraint.** The workstation runs one local model, and the generation pipeline was built for a single character.
- **What it looked like before.** Character differences were handled by special-case checks scattered through the pipeline.

**Alternatives considered.**

- **A. A separate model or process per character.** This gives clean isolation. The costs are GPU memory and twice the operational surface.
- **B. A fully separate pipeline for the second character.** This keeps the main path untouched, but duplicates logic that then drifts apart.
- **C. One shared pipeline.** Per-character profiles, character-scoped stores, and output validators sit on top of it.

**Decision.** C.

- **Profiles.** A small, immutable profile per character selects the persona definition, sampling options, fallback line, and which context features apply. The profile replaced the scattered special-case checks.
- **Shared generation.** Both characters use the same LLM queue and the same prompt composer. The speaker identity travels with the request.
- **Scoped stores.** Stream memory, chat history, and self-memory are scoped per character. Riria's turns are stored with a link to the Chiruru line they respond to.
- **Validation.** Riria's output is validated before playback. Failing output is regenerated with corrective guidance or replaced with a safe fallback. Responses from the main generation workflow also pass a persona-integrity check.

**Trade-offs.**

- ➕ One model, one queue, and one composer serve both characters. A per-character difference becomes a profile field, not a new branch in the code.
- ➕ Validator attempts and fallback use are recorded, so failures in character consistency can be audited.
- ➖ Separation is partial. Character-specific context is isolated where supported, while some memory components remain shared.
- ➖ Riria's in-show turns still run through modules beside the main path.
- ➖ Consistency checks are rule-based. A similarity-based check runs only in shadow mode, and there is no measured live consistency metric.
